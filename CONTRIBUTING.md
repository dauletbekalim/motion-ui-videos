# Contributing

Thanks for helping. Read [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) first: it explains how the template fits together, which files mirror each other, and why the defaults are what they are.

## Run the template

```bash
cd skills/motion-ui-videos/template
npm install
npm run studio           # scrub every cut and still in the browser
npm run render:reel      # sound, then picture → out/reel.mp4
```

Node 18.12 or newer (tested on Node 24). Remotion brings Chrome and ffmpeg, so there is nothing else to install. The first render fetches fonts from Google Fonts and needs a connection. The template's [README](skills/motion-ui-videos/template/README.md) lists every command.

## Render one thing at a time

Chrome and the bundler are memory-hungry. Never run two renders at once, and don't run `scripts/stills.mjs` while a render is going: on a 16 GB machine that is how you get a crash halfway through. `remotion.config.ts` already renders 2 frames at a time on 16 GiB of RAM or less; if a single render still runs out of memory, pass `--concurrency=1`. A script that calls Remotion's `bundle()` must pass an `outDir` it reuses (as `scripts/stills.mjs` does with `out/.bundle`): without one, every run leaves about 50 MB in the system temp folder.

## Tests

From `skills/motion-ui-videos/template`, after `npm install`:

```bash
node sound/test/run.mjs      # the sound engine end to end, and the clock check
node scripts/test.mjs        # the scripts: contact-sheet layout, encode filters, caption export
npm run typecheck            # TypeScript, no output when it passes
```

`run.mjs` covers the timeline math, the voices, the meter and limiter, whoosh growing, every sound tool's CLI, the places where the sound copies the picture, and a double run of `sound/design.mjs` to prove it is deterministic. It also runs `sound/test/parity.mjs`, which checks `src/lib/time.ts` and `sound/timeline.mjs` agree on every cut. Its renders go to `sound/test/out/` (gitignored). `scripts/test.mjs` renders nothing: it checks the sheet's default layout on tiny generated stills, the zscale filter strings of `scripts/encode.mjs`, and `scripts/captions.mjs` against fixtures and the demo's `src/captions.json`. `npm test` runs both. All three must pass before a PR.

If you change one side of a pair in the "Copies that must agree" table in the architecture doc, change the other side in the same PR.

## Look before you open a PR

If your change shows up in a frame, look at it. You can't judge motion from a diff.

```bash
node scripts/stills.mjs reel --marks          # a still at every mark
node scripts/sheet.mjs reel                   # → out/sheet-reel.png, and pages of 12
node scripts/stills.mjs reel --marks --safe   # the same with the safe zones drawn
node scripts/sheet.mjs reel --safe            # → out/sheet-reel-safe.png
node scripts/stills.mjs cover --safe          # a still, with its 3:4 grid crop
```

Do this for every cut your change touches. Check for clipped or overlapping text, anything a camera push shoves off the frame, captions still arriving when the next one comes, fallback fonts, and words or buttons inside the red bands. Attach the sheets to the PR (`out/` is gitignored, so they don't go in the commit).

If your change touches sound, run `node sound/design.mjs <cut> --cues` and put the relevant lines of its report in the PR: where the cut landed against its target, what the limiter did, and any change in dB (compare mixes with `node sound/tools/loudness.mjs before.wav after.wav`).

If you change the template's machinery (`src/lib/`, `src/Video.tsx`, `src/formats.ts`, `sound/engine.mjs`, `sound/timeline.mjs`, `sound/tools/`, `sound/test/`, `scripts/`), copy it to `examples/skill-promo/` too, which carries its own copy.

If your change affects what the skill tells Claude to do, try the matching prompt in `evals/evals.json` and check its assertions. If it touches the `description` in SKILL.md's frontmatter, read it against `evals/trigger-evals.json`: 20 requests, half of which should load the skill and half of which are near-misses that shouldn't. The description has to stay under 1,024 characters.

## Audio

No stock audio in git. Most stock licenses allow using a sound in a video but not sharing the raw file.

- Reference sounds go in `sound/refs/`, which is gitignored in the template and at the repo root.
- `public/sound-*.wav` is regenerated by `sound/design.mjs` on every render and is gitignored too.
- Only commit audio you made yourself, such as a sound synthesized in code, and say in the PR how it was made. The eval's `evals/fixtures/refs/swoosh.wav` is one: `make-swoosh.py` next to it rebuilds it byte for byte.

## Writing docs

This covers SKILL.md, the references, READMEs and this folder.

- Plain, direct English. Short sentences. Explain why behind every rule: the model follows reasons better than orders. No ALL-CAPS rules.
- Numbers over adjectives: seconds, px, LUFS, dB, easing curves as values.
- No marketing words ("leverage", "seamless", "robust", "comprehensive") and no emojis.
- Don't invent statistics. A platform number or retention claim needs a source you actually read, listed under "Sources" at the end of that file. Otherwise, write it as practice or a heuristic, not a fact.
- Use only API names that exist in the template. Grep for them before you write them.
- A reference starts with a one-paragraph summary, and gets a short table of contents past about 250 lines. SKILL.md stays under 500 lines.
- Code examples are TSX for scenes and plain Node ESM (`.mjs`) for sound and scripts, matching the real signatures.
- Keep the demo fictional (Lumen, Northwind). Don't add real companies' logos, and don't show numbers that aren't true.

## Housekeeping

- `.gitattributes` keeps text files LF. If you commit from Windows, check scripts still start with a clean `#!/usr/bin/env node` line.
- Every `remotion` and `@remotion/*` package stays on the same exact version. Upgrade them together with `npx remotion upgrade`.
- Keep `media/` small and optimised. `media/release/` and every `out/` folder are gitignored.
- One change per PR. Say what changed and why, in a couple of plain sentences.
- Releases: bump `version` in `.claude-plugin/plugin.json` (installed plugins only update when it goes up), tag `v<version>`, and attach the promo MP4s from `media/release/` to the GitHub release under the names the README links.
